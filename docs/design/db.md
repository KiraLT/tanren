## 1. Tables (DM §1; snake_case; `drizzle-orm/sqlite-core`, one file per aggregate in `src/schema/`)

| Table | File | Own columns (after the row columns) |
| --- | --- | --- |
| `profile` | `user.ts` | `goals` J, `constraints` J, `available_days` J, `equipment` J, `timezone` T; `UNIQUE(user_id)`, `CHECK (id = user_id)` |
| `exercise` | `exercise.ts` | `name` T, `aliases` J, `muscle_groups` J, `notes` T? |
| `plan` | `plan.ts` | `name` T, `goal` T, `start_date` T (`YYYY-MM-DD`), `status` T |
| `plan_week` | `plan.ts` | `plan_id` T FK→plan, `week_start` T, `intent` T? |
| `planned_session` | `plan.ts` | `plan_week_id` T FK→plan_week, `"order"` I, `name` T, `scheduled_date` T?, `notes` T? |
| `planned_set` | `plan.ts` | `planned_session_id` T FK→planned_session, `exercise_id` T FK→exercise, `"order"` I, `target_weight_kg` R?, `target_reps` J, `target_rpe` R?, `rest_seconds` I?, `note` T? |
| `workout_session` | `session.ts` | `started_at` T, `finished_at` T?, `planned_session_id` T? (no FK), `notes` T? |
| `workout_set` | `session.ts` | `session_id` T FK→workout_session, `exercise_id` T FK→exercise, `"order"` I, `weight_kg` R, `reps` I, `rpe` R?, `note` T?, `planned_set_id` T? (no FK), `logged_at` T |
| `sync_clock` | `sync.ts` | `user_id` T PK, `seq` I NOT NULL — not synced, no row columns (the one exception) |
| Better Auth tables | `auth.ts` (step 3) | generated by Better Auth's CLI, owned by Better Auth; not written in step 2 |

T = `text`, I = `integer`, R = `real`, J = `text` holding JSON, `?` = nullable (`Option` ↔ `NULL`);
everything else `NOT NULL`. **Row columns on every synced table:** `id` T PK (UUID), `user_id` T,
`created_at` T, `updated_at` T, `deleted_at` T?, `server_seq` I. Timestamps are the canonical
24-char ISO UTC strings produced by `Timestamp` (DM §2), so `ORDER BY`/`>` on text is chronological;
no `CURRENT_TIMESTAMP` defaults, no SQL defaults at all (the writer supplies every value).
`order` is an SQL keyword: Drizzle quotes it; hand-written SQL must write `"order"`.

- **Enums** (`status`, muscle groups, weekdays, …) are plain `text`, validated by the schemas on
  every read and write. No `CHECK`: SQLite cannot alter a CHECK without rebuilding the table, and
  DM §5 promises that adding a literal is a code-only change.
- **Foreign keys** exactly for the parents that DM §10.2 checks (`missingParent`): `plan_id`,
  `plan_week_id`, `planned_session_id` (on `planned_set`), `session_id`, `exercise_id`. D1 enforces
  FKs, so writes are ordered parents-first (`SYNC_TABLE_ORDER`). Optional links
  (`workout_session.planned_session_id`, `workout_set.planned_set_id`) have no FK: sync does not
  reject on them. No FK from `user_id` to Better Auth's `user` (step 2 must not depend on step 3's
  generated schema; every query is user-scoped anyway). `ON DELETE` stays `NO ACTION` (no hard deletes).
- **Same-user parents** are checked by the repository (`SELECT … WHERE id = ? AND user_id = ?`),
  not by composite FKs.

## 2. Indexes

| Index | Purpose |
| --- | --- |
| `<table>_user_seq_idx (user_id, server_seq)` on every synced table | pull pages by server order (DM §10.1, §11.5) |
| `plan_week (plan_id)`, `planned_session (plan_week_id)`, `planned_set (planned_session_id)`, `workout_set (session_id)` | children of a parent |
| `workout_session (user_id, started_at)` | `list_sessions`, `get_overview(period)` |
| `workout_set (user_id, exercise_id, logged_at)` | `get_exercise_history` |
| `planned_set (exercise_id)` | FK lookups on exercise |
| unique `exercise (user_id, lower(name)) WHERE deleted_at IS NULL` | DM §11.3 |
| unique `plan (user_id) WHERE status = 'active' AND deleted_at IS NULL` | one active plan |
| unique `plan_week (plan_id, week_start) WHERE deleted_at IS NULL` | DM §11.3 |

Deviation from the brief: no `(user_id, updated_at)` index. DM §10.1/§11.5 say pull follows the
server's sync order, never `updatedAt`, so `(user_id, server_seq)` replaces it. If drizzle-kit
cannot express the expression/partial indexes, add them with `drizzle-kit generate --custom`.
Unique-index violations abort a whole D1 batch, so repositories pre-check these invariants and
order writes (archive the old active plan before activating a new one).

## 3. Soft delete, LWW and the server sync order

`deleted_at` set = tombstone; nothing is ever hard-deleted. LWW decisions (compare
`updated_at`, ties to the server, clamp) belong to the sync service in step 3, not to SQL.
**`server_seq`** gives every write a monotonic position per user: each write batch starts with

```sql
INSERT INTO sync_clock (user_id, seq) VALUES (?1, 1)
  ON CONFLICT (user_id) DO UPDATE SET seq = seq + 1;
```

and every row write in that batch sets `server_seq = (SELECT seq FROM sync_clock WHERE user_id = ?1)`.
D1 serialises writes and a batch is one transaction, so positions never go backwards and a pull can
never skip a committed row. All rows of one batch share a `seq`; the pull cursor (step 3) is
`(server_seq, table rank in SYNC_TABLE_ORDER, id)`. Every write path (sync, REST, MCP, seed) goes
through repository `put`, so no write can forget the bump.

## 4. Ids

Ids are created by whoever creates the row, through `IdGenerator` (`newId(ExerciseId)`): the client
offline, the server for REST/MCP inserts, the seed's seeded generator (§7). Repositories never
generate ids; they store the id they are given. `profile.id = user_id`.

## 5. Row codecs (in `@tanren/shared`, file `row.ts`)

DB rows differ from wire rows only in JSON columns. Per entity export `XRow`: decoding a DB record
(camelCase keys after `transformResultNames`, JSON columns as strings) yields an `X` instance;
encoding an `X` yields the flat record with JSON strings. JSON columns: `goals`, `constraints`,
`availableDays`, `equipment`, `aliases`, `muscleGroups`, `targetReps`, each wrapped in
`Schema.fromJsonString(<field schema>)` (DM §12, `Schema.ts:9791`). Preferred construction: a
`Schema.Struct` of the record fields piped into `Schema.decodeTo(X)`; the engineer picks the
composition that compiles and proves it with round-trip tests VERIFY:. Also export
`ROW_TABLE: { readonly [T in SyncTable]: string }` (`set → "workout_set"`, `session →
"workout_session"`, `planWeek → "plan_week"` …). They live in `shared` because every data shape
does and because the mobile expo-sqlite store (step 6) reuses the same codecs and table names.

## 6. Client layer and repositories (`src/client.ts`, `src/repositories/*.ts`, `src/errors.ts`)

```ts
// client.ts — built per request in the Worker (step 3), from env.DB
export const D1Layer = (db: D1Database) =>
  D1Client.layer({ db, transformResultNames: Str.snakeToCamel, transformQueryNames: Str.camelToSnake })
// errors.ts — internal, never on the wire
export class PersistenceError extends Data.TaggedError("PersistenceError")<{
  readonly operation: string; readonly cause: unknown }> {}
```

`Str` = `String` from `effect` (`snakeToCamel`/`camelToSnake` exist in 4.0.5 `String.ts`). One
`Context.Service` per aggregate with `static readonly layer: Layer<Repo, never, D1Client>`:
`ProfileRepo`, `ExerciseRepo`, `PlanRepo` (plan, planWeek, plannedSession, plannedSet),
`SessionRepo` (session, set), merged by `Repositories.layer`. Every method takes `userId: UserId`
first and every SQL statement contains `user_id = ?`. `SqlError`/`SchemaError` map to
`PersistenceError`. Step-2 surface (step 3 adds endpoint queries and the pull query):

```ts
interface ExerciseRepoShape {
  readonly get: (userId: UserId, id: ExerciseId) => Effect<Option<Exercise>, PersistenceError>
  readonly list: (userId: UserId, opts: { readonly includeDeleted: boolean }) =>
    Effect<ReadonlyArray<Exercise>, PersistenceError>
  /** Upsert full rows in one D1 batch: clock bump first, then one INSERT … ON CONFLICT(id) DO UPDATE
   *  per row (≤ 100 bound params per statement); SET skips id, user_id, created_at and immutable
   *  parent ids; `WHERE <table>.user_id = excluded.user_id`. Fails with Forbidden (shared) if any
   *  row's userId ≠ userId. No LWW here: callers decide. */
  readonly put: (userId: UserId, rows: ReadonlyArray<Exercise>) => Effect<void, PersistenceError | Forbidden>
}
```

Same shape for each entity (`PlanRepo.getPlan/listPlans/putPlans`, `putPlanWeeks`,
`putPlannedSessions`, `putPlannedSets`, plus `currentPlan(userId): Option<{ plan, weeks,
sessions, sets }>`; `SessionRepo.getSession/listSessions({ from, to })/putSessions/listSets(sessionId)/putSets`;
`ProfileRepo.get/put`). Lists sort by DM §11.2 `(order, created_at, id)` where `order` exists.
`D1Client.batch` signature and whether it accepts `effect/sql` statements: **VERIFY:** from
`@effect/sql-d1@4.0.5` types; fallback is compiling statements and calling `db.batch`. Statement
count per batch vs the 50-queries-per-invocation Free limit is unknown (researcher question).

## 7. Seed (LD §1, "Seed")

- `src/seed/month.ts`: `seedMonth({ userId, seed, endDate }): Effect<SeedData, never, IdGenerator>`
  where `SeedData` has one readonly array per `SyncTable` (shared entity instances). Pure apart from
  `Random` and `IdGenerator`; deterministic via `Random.withSeed(effect, seed)` (4.0.5 `Random.ts:315`)
  and `seededIdGenerator`: an `IdGenerator` layer whose `next` formats 16 `Random` bytes as a v4 UUID
  (not `IdGenerator.layerTest`: its first id equals the LD seed user id). Timestamps derive from
  `endDate` only, never `Clock`.
- Content for user `00000000-0000-4000-8000-000000000001`: profile (strength + hypertrophy, Mon/Wed/
  Fri/Sat, barbell/rack/bench/dumbbells/pullUpBar, Europe/Berlin); ~14 exercises with aliases; one
  active upper/lower plan with 5 weeks × 4 planned sessions × 4–6 exercises × 3–5 planned sets
  (`Exact`/`Range` targets, rest 90–180 s); 30 days ending `endDate`: ~14 logged sessions linked to
  planned sessions, 2 missed, 1 unplanned, +2.5 kg/week on compounds, RPE 6.5–9.5, a few notes, one
  soft-deleted set, one deload week. Every row must decode with its shared schema (test).
- Runner `apps/worker/scripts/seed.ts` (LD): `getPlatformProxy({ configPath: "wrangler.jsonc",
  persist: { path: <abs>/apps/worker/.wrangler/state/v3 }, remoteBindings: false })` → `D1Layer(env.DB)`
  → repositories' `put` in `SYNC_TABLE_ORDER`, chunked; `endDate` defaults to today (CLI flag
  `--end YYYY-MM-DD`), `seed` defaults to `1`. Run with `tsx` (`@4.23.15`, executed under pnpm in R §2).
  Idempotent: same ids + upsert. Reset = LD `db:reset`.

## 8. Tests

Repository tests run against a real migrated local D1 in `workerd` using
`@cloudflare/vitest-plugin@1.4.6` (peers vitest 5; `@cloudflare/vitest-pool-workers` peers vitest 4,
so it is out — LD §3): `packages/db/vitest.config.ts` uses `cloudflareTest({ wrangler: { configPath:
"./wrangler.test.jsonc" } })` with binding `DB`, `migrations_dir: "migrations"`, and a setup file
calling `applyD1Migrations(env.DB, …readD1Migrations("./migrations"))`; each test file gets isolated
storage. `@effect/vitest` inside workerd is VERIFY: (first thing the harness task proves). Fallback
if it does not run: Node `getPlatformProxy` with a fresh temp `persist.path` per file, migrations
applied by splitting the SQL on `--> statement-breakpoint` into one `db.batch` (mechanism V-run in R §2).
Plain SQLite (better-sqlite3) is rejected: native build under pnpm 12 and it would not exercise
`D1Client`. Pure tests (`row.ts`, `seed/month.ts`) run in plain Node Vitest. Required cases: user
scoping (user B never sees or overwrites A's rows), FK rejection of missing parents, partial unique
indexes, `server_seq` strictly increases across batches, upsert keeps immutable columns, codec/table
column parity (ADR-0006 consequence).
